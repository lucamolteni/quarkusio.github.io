== Overview

You want database access: you want your application data to be persisted somewhere, you have an external database to query, and you're wondering where to start?
In this guide we'll walk you through how to do it the Quarkus way.


== Prerequisites

You need to have the quarkus cli tool installed. [Here the instructions on how to install it](https://quarkus.io/guides/cli-tooling)

== Introduction

You're working on a physical bookstore website, in which you want users to be able to browse books with titles.
In this tutorial, we won't deal with the frontend and the user interface, we just want to connect to the database.

We'll start this tutorial by creating a new empty quarkus application. The easiest way to do so is to have quarkus CLI tool available:

[source,bash]
----
quarkus create app --name="Quarkus Data Tutorial" quarkus-data-tutorial --platform-bom=io.quarkus.platform:quarkus-bom:3.37.0.CR1
----

Let's start by importing the extension:

[source,bash]
----
cd quarkus-data-tutorial

quarkus extension add quarkus-data-hibernate
quarkus extension add quarkus-jdbc-postgresql
----

The first dependency, `quarkus-data-hibernate`, is the Quarkus extension that provides everything you need for database access.
The second dependency, `quarkus-jdbc-postgresql`, is the JDBC driver that tells Quarkus how to talk to a PostgreSQL database. If you're using a different database (MySQL, MariaDB, H2, etc.), pick the corresponding `quarkus-jdbc-*` driver instead. Quarkus Data Hibernate cannot work without a JDBC driver.
That's all you need to start querying your database.

Run now quarkus in a separate tab of your terminal with

[source,bash]
----
quarkus test
----

You don't need to restart quarkus testing, it'll run test continously after every change.

Now create an `import.sql` file in `src/main/resources/` to prepopulate your database, this will be useful for this tutorial:

[source,bash]
----
cat > src/main/resources/import.sql << 'EOF'
CREATE TABLE IF NOT EXISTS Book (
    id BIGSERIAL PRIMARY KEY,
    title VARCHAR(255),
    isbn VARCHAR(20),
    price INT
);

DELETE FROM Book;

INSERT INTO Book (id, title, isbn, price) VALUES (1, 'Effective Java', '978-0134685991', 45);
INSERT INTO Book (id, title, isbn, price) VALUES (2, 'Clean Code', '978-0132350884', 40);
INSERT INTO Book (id, title, isbn, price) VALUES (3, 'Domain-Driven Design', '978-0321125217', 55);
INSERT INTO Book (id, title, isbn, price) VALUES (4, 'Refactoring', '978-0134757599', 50);
INSERT INTO Book (id, title, isbn, price) VALUES (5, 'The Pragmatic Programmer', '978-0135957059', 42);
EOF
----

This SQL script creates a `Book` table with four columns (`id`, `title`, `isbn`, `price`) and inserts five books into it.
While developing, Quarkus imports this SQL file automatically at startup when the database is empty, so you'll have data to query right away.

TIP: JDBC connection are called "Data Source" in Quarkus. In dev mode, if you don't configure a datasource, Quarkus will automatically start a PostgreSQL container for you via Dev Services. This means you can run `quarkus dev` and start coding without installing or configuring a database.

== Simple SQL query

The simplest thing you can do to access your database is to write native SQL queries directly, create a file called in the package `org.acme` called `BookService`:

[source,java]
----
package org.acme;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;
import org.hibernate.StatelessSession;

import java.util.List;

@ApplicationScoped // <1>
public class BookService {

    record BookRecord(Long id, String title, String isbn, int price) {} // <2>

    @Inject
    StatelessSession session; // <3>

    public List<BookRecord> findByTitle(String title) {
        return session.createNativeQuery("""
                SELECT id, title, isbn, price FROM Book
                WHERE title = :title
                """, BookRecord.class) // <4>
                .setParameter("title", title)
                .getResultList(); // <5>
    }

    public List<BookRecord> cheaperThan(int maxPrice) {
        return session.createNativeQuery("""
                SELECT id, title, isbn, price FROM Book
                WHERE proce < :maxPrice
                """, BookRecord.class)
                .setParameter("maxPrice", maxPrice)
                .getResultList();
    }
}
----
<1> `@ApplicationScoped` makes this class a CDI bean. Quarkus creates a single instance and manages its lifecycle for you. You can then inject it anywhere you need it.
<2> A Java record that maps to the columns returned by the SQL query. Each field name must match a column name in the result set.
<3> `@Inject` asks Quarkus to provide a database session. A `StatelessSession` is the simplest entry point to Hibernate.
<4> `createNativeQuery(...)` sends raw SQL to the database. The `:title` syntax is a named parameter, Hibernate will substitute the value you pass via `setParameter`.
<5> Executes the query and returns the results as a `List`.

[WARNING]
====
This example uses named parameters (`:title`) and `setParameter` to bind values safely.
If you think it's a good idea to concatenate strings into your queries instead, please don't: it exposes your application to SQL injection attacks.
====

If SQL is enough for you, this is a perfectly valid use case of `quarkus-data-hibernate`.
But as your application grows, you'll want a place to group all your query methods together rather than scattering them across service classes.

We can now create a test in `src/test/java/org/acme/BookServiceTest.java` that will check everything is working correctly:

[source,java]
----
package org.acme;

import io.quarkus.test.junit.QuarkusTest;
import jakarta.inject.Inject;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.*;

@QuarkusTest // <1>
public class BookServiceTest {

    @Inject
    BookService bookService; // <2>

    @Test
    void shouldFindBookByTitle() {
        var books = bookService.findByTitle("Effective Java"); // <3>
        assertEquals(1, books.size());
        assertEquals("Effective Java", books.getFirst().title());
    }

    @Test
    void shouldReturnEmptyListForUnknownTitle() {
        var books = bookService.findByTitle("Unknown Book");
        assertTrue(books.isEmpty());
    }
}
----
<1> `@QuarkusTest` starts the full Quarkus application for the test, including the database and Dev Services. The data from `import.sql` is loaded automatically.
<2> We inject our `BookService` just like we would in application code.
<3> We query for a book we know exists in `import.sql` and verify it's returned.

If you have `quarkus test` running in another terminal, this test will run automatically as soon as you save the file.

Even though raw SQL is a perfectly valid approach, it has a few problems.
First of all, type safety: nobody is going to validate your queries at compile time.

Let's add a test for `cheaperThan` to our `BookServiceTest`:

[source,java]
----
@Test
void shouldFindCheaperBooks() {
    var books = bookService.cheaperThan(45);
    assertEquals(2, books.size()); // Clean Code (40) and The Pragmatic Programmer (42)
}
----

The console in `quarkus test` will show

[source,shell]
----
org.hibernate.exception.SQLGrammarException: JDBC exception executing SQL [ERROR: column "proce" does not exist

Hint: Perhaps you meant to reference the column "book.price".

Position: 26] [SELECT * FROM Book

WHERE proce < ?
----

This test will fail at runtime with a SQL error because the column `proce` doesn't exist.
Did you initially spot the typo in `cheaperThan`? The column is called `price`, not `proce`, but the compiler won't tell you.
You're probably going to have integration tests to catch that, but it would be faster if the compiler could validate it earlier.

You can fix the test by modifying the `BookService.java` file:

[source,java]
----
    public List<BookRecord> cheaperThan(int maxPrice) {
        // <1>
        return session.createNativeQuery("""
                SELECT * FROM Book
                WHERE price < :maxPrice
                """, BookRecord.class)
            .setParameter("maxPrice", maxPrice)
            .getResultList();
    }
----
<1> Change `proce` to `price` here

Writing SQL by hand makes sense for very simple scenarios, or when you need database-specific features such as window functions, recursive functions and similar advanced patterns.

== Entities and repositories

We can avoid all these problems by mapping our table to a Java class and defining a repository for it.
We now introduce the concept of Entity, for now we might think of it as a Java class that maps to a Database Table.

Create a file called in the package `org.acme` called `Book.java`:

[source,java]
----
package org.acme;

import io.quarkus.hibernate.panache.PanacheRepository;
import io.quarkus.hibernate.panache.WithId;
import jakarta.data.repository.Find;
import jakarta.data.repository.Query;
import jakarta.persistence.Entity;

import java.util.List;

@Entity // <1>
public class Book extends WithId.AutoLong { // <2>
    public String title; // <3>
    public String isbn;
    public int price;

    public interface Repo extends PanacheRepository<Book> { // <4>
        @Find
        List<Book> findByTitle(String title); // <5>

        @Query("where price < :maxPrice order by title")
        List<Book> cheaperThan(int maxPrice); // <6>
    }
}
----
<1> Tells Hibernate that this class maps to a database table. Hibernate will use the class name as the table name and the field names as column names.
<2> Gives the entity a generated `Long` id field automatically.
<3> These public fields map to columns in the `Book` table. Hibernate reads and writes these fields directly.
<4> Defines a repository: a place to put all your query methods for `Book`. By nesting it inside the entity, the queries and the data they operate on live together.
<5> `@Find` tells Quarkus Data Hibernate to generate a query based on the method's parameter names. `findByTitle(String title)` becomes a query that matches the `title` field on `Book`. Parameters are inferred from the method signature.
<6> `@Query` lets you write an HQL fragment when you need more control. It avoid the need to write `select b from Book`. The entity type is inferred from the return type `List<Book>`.

Now that we have an entity, Hibernate can generate the table for us. You can remove the `CREATE TABLE` statement from `import.sql` and just keep the `INSERT` statements. This is a much type safer approach and avoids you to keep files aligned.

The repository is an interface, so you might wonder who implement this. It's the Hibernate annotation processor, which is a key component in this solution.
During compilation, it reads your entity model and your repository interfaces, validates everything, and generates implementation classes under `target/generated-sources/annotations/`.
These generated classes are compiled together with your entities and wired up automatically by Quarkus. They are also simple to read, in case you want to understand how it works internally.

To enable it, add the processor to your build configuration:

[source,xml,role="primary asciidoc-tabs-target-sync-cli asciidoc-tabs-target-sync-maven"]
.pom.xml
----
<plugin>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <annotationProcessorPathsUseDepMgmt>true</annotationProcessorPathsUseDepMgmt>
        <annotationProcessorPaths>
            <path>
                <groupId>org.hibernate.orm</groupId>
                <artifactId>hibernate-processor</artifactId>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
----

[source,gradle,role="secondary asciidoc-tabs-target-sync-gradle"]
.build.gradle
----
annotationProcessor enforcedPlatform("${quarkusPlatformGroupId}:${quarkusPlatformArtifactId}:${quarkusPlatformVersion}")
annotationProcessor 'org.hibernate.orm:hibernate-processor'
----

Now if you make the same kind of typo we had earlier, i.e. `findByTitle(String tilte)`, the build fails:

[source]
----
error: no matching field named 'tilte' in entity class 'org.acme.Book'
----

== Creating entities

So far we've been reading data, but our bookstore is crowdsourced: users can add books they want to share.
We need to persist new books to the database.

Let's update our `Book` to extend `WithId.AutoLong` and implement `PanacheEntity.Stateless`, which gives us lifecycle operations directly on the entity:

[source,java]
----
@Entity
public class Book extends WithId.AutoLong implements PanacheEntity.Stateless { // <1>
    public String title;
    public String isbn;
    public int price;

    public interface Repo extends PanacheRepository.Stateless<Book, Long> { // <2>
        @Find
        List<Book> findByTitle(String title);

        @Query("where price < :maxPrice order by title")
        List<Book> cheaperThan(int maxPrice);
    }
}
----
<1> This is the new part: `implements PanacheEntity.Stateless` gives our `Book` class methods to create, delete or update books without the need to use specific methods in repositories.

<2> The repository also changed to `PanacheRepository.Stateless<Book, Long>` to specify the .
// TODO LUCA ^ verify the Long type parameter is really needed

Now we can write a service that lets users contribute a new book:

[source,java]
----
@ApplicationScoped
public class CrowdSourceService {

    @Transactional // <1>
    public void contributeNewBook(String title, String isbn) {
        Book book = new Book();
        book.title = title;
        book.isbn = isbn;
        book.price = 0;
        book.insert(); // <2>
    }
}
----
<1> Wraps the method in a database transaction. This is required to define the scope of your operations, so that related operations might be committed or rollbacked together. This case is very simple.
<2> `insert()` immediately executes an `INSERT` statement against the database.

[NOTE]
====
If you're an experienced Hibernate user, you'll find this part very different to what you're used to.
When you call `insert()`, `update()`, or `delete()`, an operation is triggered against the database.
Managed entities are nowhere to be seen, and the idea of a detached object vs a persisted object is missing.
This is intentional: it's a simpler model that uses `StatelessSession` under the covers.
In this mode every change to an object requires an explicit save operation.
If you're not interested in this style and want the full power of managed entities, skip ahead to <<managed-session>>.
====

=== About entity identifiers

`WithId.AutoLong` is more powerful than Hibernate's traditional `@Id @GeneratedValue` pair: there are variants for different ID types out of the box:

- `WithId.AutoLong` — a generated `Long` id
- `WithId.AutoUUID` — a generated `UUID` id
- `WithId.AutoString` — a generated `String` id

Of course you can always use `@Id` and `@GeneratedValue` directly if you prefer, or if you need a custom ID strategy.
See the xref:quarkus-data-hibernate.adoc#_about_entity_identifiers[reference guide] for the full list of options.

== Managed session

We said that with a stateless session, every change you make to an entity requires an explicit call to `insert()`, `update()`, or `delete()`.
A managed session works differently: you don't need to think about when the data is going to be persisted to the database.
Hibernate keeps track of all the changes you make to your objects and, when the transaction commits, executes the most efficient series of SQL operations it can.

To slightly complicate our example Let's also add an author to our bookstore, linked to `Book` with a `@ManyToOne` association:

[source,java]
----
@Entity
public class Author extends WithId.AutoLong {
    public String name;
}
----

Now to switch to a managed session, implement `PanacheEntity.Managed` instead of `PanacheEntity.Stateless`.

[source,java]
----
@Entity
public class Book extends WithId.AutoLong implements PanacheEntity.Managed { // <1>
    public String title;
    public String isbn;
    public int price;
    @ManyToOne(cascade = CascadeType.PERSIST) // <2>
    public Author author;

    public interface Repo extends PanacheRepository<Book> { // <3>
        @Find
        List<Book> findByTitle(String title);

        @Query("where price < :maxPrice order by title")
        List<Book> cheaperThan(int maxPrice);
    }
}
----
<1> `PanacheEntity.Managed` replaces `PanacheEntity.Stateless`. This tells Hibernate to track this entity in its internal stateful persistence context
<2> `@ManyToOne` creates a relationship between `Book` and `Author`. The `cascade = CascadeType.PERSIST` means that when you persist a `Book`, Hibernate will automatically persist its `Author` too if it's new.
// TODO Luca Persist is not needed probably!
<3> The repository goes back to `PanacheRepository<Book>` (not `Stateless`) since we're now using managed sessions.

Now we can persist a book with its author in a single call, Hibernate takes care of the ordering and persists both:

[source,java]
----
@ApplicationScoped
public class CrowdSourceService {

    @Transactional
    public void contributeNewBook(String title, String isbn, String authorName) {
        Author author = new Author();
        author.name = authorName;

        Book book = new Book();
        book.title = title;
        book.isbn = isbn;
        book.price = 0;
        book.author = author;
        book.persist(); // <1>
    }
}
----
<1> `persist()` (note that is different than: `insert()`) doesn't execute SQL immediately. It tells Hibernate "this object is new, make sure it'll persisted in the DB." Because `Book.author` has `cascade = CascadeType.PERSIST`, we don't need to persist the `Author` separately. Hibernate figures out that the author is new, inserts it first (to get its ID), then inserts the book with the correct foreign key.

Compare it to what this would have been with a stateless session instead:

[source,java]
----
@Transactional
public void contributeNewBook(String title, String isbn, String authorName) {
    Author author = new Author();
    author.name = authorName;
    author.insert();

    Book book = new Book();
    book.title = title;
    book.isbn = isbn;
    book.price = 0;
    book.author = author;
    book.insert();
}
----

This particular case is not incredibly less compac than the one before. IN the Stateless Session version we have to insert, one for entity, and in the managed we have a single persist at the end of it. More complicated cases (perhaps involving collections will show more explicit advantages)
// Luca use a OneToMany example
This shows the philosophy we've been trying to introduce since the https://quarkus.io/blog/introducing-quarkus-data/[blog post]: we want to make sure that simple things are easy, but more complex things are possible.

== Reactive

If you're already using reactive APIs in your application (Quarkus Messaging, reactive REST clients, Vert.x), you want your database access to compose naturally with them without blocking the event loop.
Quarkus Data Hibernate lets you experiment with both blocking and reactive to see what works best for your case. The same entity model works unchanged with a reactive driver.

First, add the reactive dependencies:

[source,xml,role="primary asciidoc-tabs-target-sync-cli asciidoc-tabs-target-sync-maven"]
.pom.xml
----
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-hibernate-reactive</artifactId>
</dependency>
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-reactive-pg-client</artifactId>
</dependency>
----

[source,gradle,role="secondary asciidoc-tabs-target-sync-gradle"]
.build.gradle
----
implementation("io.quarkus:quarkus-hibernate-reactive")
implementation("io.quarkus:quarkus-reactive-pg-client")
----

`quarkus-hibernate-reactive` adds the reactive Hibernate engine, which uses non-blocking I/O under the covers instead of JDBC.
`quarkus-reactive-pg-client` is the reactive equivalent of `quarkus-jdbc-postgresql`. It provides a non-blocking PostgreSQL driver built on Vert.x. As its blocking counterpart, it's mandatory for Quarkus Data Hibernate to work.

Now let's change only the minimal part of the code you need to try reactive. Let's add a second nested repository for reactive operations:

[source,java]
----
@Entity
public class Book extends WithId.AutoLong implements PanacheEntity.Managed {
    public String title;
    public String isbn;
    public int price;
    @ManyToOne(cascade = CascadeType.PERSIST)
    public Author author;

    public interface Repo extends PanacheRepository<Book> { // <1>
        @Find
        List<Book> findByTitle(String title);

        @Query("where price < :maxPrice order by title")
        List<Book> cheaperThan(int maxPrice);
    }

    public interface ReactiveRepo extends PanacheRepository.Reactive<Book, Long> { // <2>
        @Find
        Uni<List<Book>> findByTitle(String title); // <3>
    }
}
----
<1> The blocking repository stays unchanged.
<2> A new reactive repository for the same entity. Both repositories can coexist
<3> The operations in the return `Uni<T>` instead of `T`. `Uni` is a Mutiny reactive type that represents a value that will be available in the future. Instead of blocking the thread, the method returns immediately and emits the result when the query completes.

Suppose our bookstore receives a stream of advertised books from a message queue, and we want to check which ones we don't already have in our catalog.
Using Quarkus Messaging and the reactive repository, the entire pipeline stays non-blocking:

[source,java]
----
@ApplicationScoped
public class BookSuggestionService {

    @Inject
    Book.ReactiveRepo books; // <1>

    @Incoming("advertised-books") // <2>
    @Outgoing("suggestions") // <3>
    public Multi<String> suggestNewBooks(Multi<String> advertisedIsbns) {
        return advertisedIsbns
            .onItem().transformToUniAndMerge(isbn ->
                books.findByTitle(isbn) // <4>
                    .map(found -> found.isEmpty() ? isbn : null)
            )
            .select().whereNonNull();
    }
}
----
<1> We inject `Book.ReactiveRepo` instead of `Book.Repo`.
<2> `@Incoming` connects the method to a message channel named `advertised-books`. Messages arrive as a `Multi<String>` — a reactive stream of ISBNs.
<3> `@Outgoing` sends the method's output to the `suggestions` channel. These are Quarkus Messaging annotations that work with Kafka, AMQP, or in-memory channels for testing.
<4> For each ISBN, we check the database. If no book is found (`found.isEmpty()`), the ISBN is forwarded. The entire pipeline runs without blocking any thread.

The entity hasn't changed, it still has `.insert()` that blocks the thread.
If you also need to persist entities reactively, you could access the entity as a managed reactive entity and save it from there

[source,java]
----
 book.managedReactive().save()
----

You might notice we're not calling `book.persist()` like we did in the blocking version. That's because the entity's lifecycle methods (`persist()`, `delete()`) are tied to the entity's interface type. Since `Book` implements `PanacheEntity.Managed` (blocking), calling `book.persist()` would block. To persist reactively without changing the entity model, we use a repository `@Save` method instead.

For the full details on reactive sessions, stateless reactive, and combining blocking and reactive code, see the xref:quarkus-data-hibernate.adoc#_let_s_get_reactive[reference guide].

== Going further

Everything you've seen in this guide is built on top of https://jakarta.ee/specifications/data/[Jakarta Data] and https://jakarta.ee/specifications/persistence/[Jakarta Persistence].
You can use these raw components directly for more advanced scenarios: for instance, you could define repositories as standalone interfaces outside of entities, and the annotation processor will still generate the query implementations for you.
You can also inject the `Session` or `StatelessSession` at any time and do things manually, Hibernate style — as we did in the very first example of this guide.
The xref:quarkus-data-hibernate.adoc[reference guide] covers the full API surface.
