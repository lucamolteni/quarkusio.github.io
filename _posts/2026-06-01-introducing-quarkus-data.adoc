== Quarkus Data: One Gateway for Data Access

Having discussed current database access patterns in conferences, meetings and user feedback sessions, we know that the current implementation of Panache, which we'll call Panache 1 in this blog post, is popular as a data access mechanism, albeit the naming is not as popular as we wanted.
Despite Panache 1's popularity, we discovered that there is some confusion on exactly what extension to use.
Should a user that needs database access in a Quarkus application use the Hibernate extension, the Hibernate Reactive extension, Panache, or something else?
Given that Hibernate is currently the most popular extension in Quarkus (as most applications will need persistence on the database) you might imagine that this confusion is creating some of friction.

Try it yourself: create a Quarkus app with the CLI, then search for a database extension:

[source,bash]
----
quarkus create app myapp
cd myapp
quarkus extension add jpa
----

image::extension-search-jpa.png[Searching for JPA returns 16 extensions]

That's a lot of results. Some of them are not obviously related but the ones on top are seriously misleading.
And if you try searching for "database" instead, it's even worse:

image::extension-search-database.png[Searching for database returns even more extensions]

Which one do you pick?

You might have read https://quarkus.io/blog/hibernate-panache-next/[this blog post] that talks about Panache Next, the new version of Panache that we're currently developing.
This blog post is about its natural evolution.

== A brief history of Panache

This situation is admittedly confusing, but it didn't happen by accident. Every one of those extensions exists because it solves a real problem.
To understand how we got here, we need to go back to the early days of Quarkus.

Developers wanted a simple way to avoid writing repetitive data access code: define an entity, get basic CRUD operations, and declare queries in a single place without writing similar query methods by hand.
Also, users love the idea of the "repository class", a class that will hold such queries and some helpers to avoid writing code.
At the time, there was no standard repository pattern for Hibernate, so the Quarkus team created Panache to fill that gap.
Panache provided a repository pattern, a single place to define queries for each entity, and also offered an active record pattern for those who preferred attaching persistence methods directly to their entities.

== Introducing Jakarta Data

In 2022, the Eclipse Foundation https://projects.eclipse.org/projects/ee4j.data/reviews/creation-review[approved the creation] of a new specification called https://jakarta.ee/specifications/data/[Jakarta Data], led by Otávio Santana.
The goal was to standardize the repository pattern across both SQL and NoSQL databases, drawing inspiration from Spring Data, Apache DeltaSpike, Jakarta NoSQL, and Quarkus itself.

Jakarta Data does not depend on or include Jakarta Persistence, the "old" specification which is very common in Jakarta EE (formerly known as Java EE) scenarios: it's a separate specification.
Hibernate's implementation uses Hibernate under the covers, but Jakarta Data is https://jakarta.ee/learn/specification-guides/nosql-and-persistence-explained/[designed to work with any kind of database, relational or not].
You declare a repository interface, and an annotation processor generates the implementation at compile time, including full type checking of queries and parameter bindings against your entity model.

Gavin King, the creator of Hibernate, was https://www.youtube.com/watch?v=Qr7R2pLnBDM[initially skeptical] of repositories — his argument being that the `EntityManager` already serves as a generic repository, and wrapping it in another layer only takes you further from the database.
What changed his mind was annotation processing: for the first time, repository methods could be validated at compile time, catching bugs as you type rather than at runtime.

https://jakarta.ee/specifications/data/1.0/[Jakarta Data 1.0] shipped in 2024 as part of Jakarta EE 11 with stateless repositories — explicit insert, update, delete operations with no persistence context, backed by Hibernate's `StatelessSession`.
Jakarta Data 1.1, currently in development, adds stateful operations (`@Persist`, `@Merge`, `@Remove`) for developers who want persistence context semantics.

Having now Jakarta Data, most of the technology that Panache was implementing is standardized in a common specification, so it was natural for the Quarkus team to start supporting it.

== Introducing Quarkus Data

Quarkus Data is an umbrella project for data access in Quarkus.
It groups all data access modules under a single name, making it easier to find documentation and understand how the pieces fit together.

[NOTE]
.Why "Quarkus Data" and not "Panache 2"?
====
The Panache name never quite caught on with users, and it could have misled them into thinking this was a new improved implementation of Hibernate, which it definitely is not.
We chose "Data" because the project is built on Jakarta Data, and it incidentally helps users migrating from Spring as they're already used to the "Data" naming.
It's also an opportunity to create an umbrella that covers both SQL and NoSQL under the same name.
====

Under the Quarkus Data umbrella, there are specific modules for different backends.
The first one is **Quarkus Data Hibernate**, for relational databases.
In the future, additional modules like Quarkus Data MongoDB could follow the same model for NoSQL databases.

== Quarkus Data Hibernate

Quarkus Data Hibernate is the entry point for relational database access in Quarkus.
If you need to talk to a database, this is the one extension you add:

[source,bash]
----
quarkus extension add quarkus-data-hibernate
----

Or in your `pom.xml`:

[source,xml]
----
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-data-hibernate</artifactId>
</dependency>
----

Currently, the Hibernate annotation processor needs to be configured explicitly in your build.
We plan to make this automatic, but for now add the following to your `maven-compiler-plugin` configuration:

[source,xml]
----
<plugin>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <annotationProcessorPaths>
            <path>
                <groupId>org.hibernate.orm</groupId>
                <artifactId>hibernate-processor</artifactId>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
----

Let's walk through what it offers, in order of complexity.

=== Simple SQL query

The simplest thing you can do to access your database is to write native SQL queries directly, without defining any entity.
Inject a `StatelessSession` and use `createNativeQuery`, mapping results to a Java record:

[source,java]
----
@Path("/db")
public class DatabaseResource {
    @Inject
    StatelessSession session;

    record ConnectionInfo(int pid, String usename, String application_name, String state) {}

    @GET
    @Path("/connections")
    public List<ConnectionInfo> connections(@QueryParam("state") String state) {
        return session.createNativeQuery("""
                SELECT pid, usename, application_name, state
                FROM pg_stat_activity
                WHERE datname = current_database()
                  AND (state = :state OR CAST(:state AS TEXT) IS NULL)
                """, ConnectionInfo.class)
            .setParameter("state", state)
            .getResultList();
    }
}
----

[WARNING]
====
This example uses named parameters (`:state`) and `setParameter` to bind values safely.
If you think it's a good idea to concatenate strings into your queries instead, please don't: it exposes your application to SQL injection attacks.
====

If SQL is enough for you, this is a perfectly valid example of `quarkus-data-hibernate`.
Inlining the queries inside the endpoints can be enough for very simple example, but it becomes harder to create abstractions.
We can then put these queries inside a repository, similar to what you can do in other frameworks such as Spring Data JDBC.
Using Hibernate's `@SQL` annotation, the annotation processor generates the implementation at compile time.
A standard `@NativeQuery` annotation is being added to Jakarta Persistence (https://github.com/jakartaee/persistence/issues/991[jakartaee/persistence#991], https://github.com/jakartaee/persistence/pull/992[jakartaee/persistence#992]) and will be usable as an alternative to `@SQL` in a future release:

[source,java]
----
@Repository
public interface DatabaseInfo {

    @SQL("""
        SELECT pid, usename, application_name, state
        FROM pg_stat_activity
        WHERE datname = current_database()
          AND (state = :state OR CAST(:state AS TEXT) IS NULL)
        """)
    // @NativeQuery will be supported in Jakarta Persistence 4.0
    List<ConnectionInfo> activeConnections(String state);
}
----

Working with raw SQL is a perfectly valid approach for production use.
Hibernate executes these queries as prepared statements, and `StatelessSession` supports JDBC batching for insert, update, and delete operations.
Connection pooling and session lifecycle are managed by the container, and transactions work with `@Transactional` as expected.
However, native SQL queries are not validated at compile time: correctness should be verified with integration tests.
When you're ready for a better developer experience, you can define entities and leverage the full power of the annotation processor.

=== Introducing Entity Mapping and Repositories

Entity mapping opens a whole new world of features, and it enables the true power of Hibernate.
I won't state every feature Hibernate provides as there are plenty of materials everywhere, but let's focus on correctness and how much easier it is to check, which is particularly useful to have a fast feedback loop, for humans and AI agents.

Let's map our business logic using classes.
We're making an online physical book store, so we'll have books, users and orders.
By defining entity classes, we don't need to generate the schema manually: we can trust Quarkus and Hibernate to create the proper tables and focus on the business logic instead.

[source,java]
----
@Entity
public class Book {
    @Id @GeneratedValue
    public Long id;
    public String title;
    public String isbn;
    public int price;
}

@Repository
public interface BookRepository {

    @Save
    Book save(Book book);

    @Find
    Optional<Book> findByIsbn(String isbn);

    @Find
    List<Book> findByTitle(String title);

    @Query("where price < :maxPrice order by title")
    List<Book> cheaperThan(int maxPrice);
}
----

`@Find` methods derive the query from parameter names: `findByIsbn(String isbn)` matches the `isbn` field on `Book`.
If you rename the parameter to something that doesn't match, say `findByIsbn(String i)`, the build fails:

[source]
----
error: no matching field named 'i' in entity class 'org.acme.Book'
----

This is caught at compile time by the Hibernate annotation processor, not at application startup.
Other frameworks https://github.com/spring-projects/spring-data-jpa/issues/1690[traditionally validate queries at startup], which means you only discover mistakes when the application boots, or worse, in production.

[NOTE]
====
To validate fields at compile time, Quarkus Data Hibernate needs to know the model of your tables: how they are structured and what fields they contain.
This is what the entity class provides.
Spring's `JdbcTemplate` infers the query from the name of the method, which is brittle and can lead to errors at runtime.
Entity mapping can use very complex features, but it's also perfectly fine to define a simple entity class just for query mapping purposes.
The same table can even be mapped by different classes for different query needs.
Either way, it's a good starting point for building a full entity model when you need one.
====

The annotation processor also generates readable source code.
You can open `BookRepository_.java` in `target/generated-sources/annotations/` and see the exact queries that will be executed, making debugging straightforward.

Here's a possible REST endpoint implementation that uses the repository:

[source,java]
----
@Path("/books")
public class BookResource {

    @Inject
    BookRepository books;

    @POST
    @Transactional
    public Book create(Book book) {
        return books.save(book);
    }

    @GET
    @Path("/by-isbn/{isbn}")
    public Optional<Book> byIsbn(@PathParam("isbn") String isbn) {
        return books.findByIsbn(isbn);
    }

    @GET
    @Path("/cheap")
    public List<Book> cheap(@QueryParam("max") int maxPrice) {
        return books.cheaperThan(maxPrice);
    }
}
----

If you've used Hibernate before, you might notice that this example doesn't inject any session or entity manager.
That's intentional: Jakarta Data repositories use Hibernate's `StatelessSession` under the covers, the same one we injected explicitly in the <<Simple SQL query,first example>>.
A stateless session gives you the entity model (type-safe queries, parameter binding, schema validation) without a persistence context.
Every operation is immediate, so you don't need to think about entity lifecycle states.

=== Managed session with a persistence context

If on the other hand you want Hibernate to handle the full entity lifecycle, `quarkus-data-hibernate` also gives you Jakarta Persistence and the managed `Session`.
This is where you get lazy loading, automatic dirty checking, batch inserts, and the first-level cache.

Let's add an author to our bookstore:

[source,java]
----
@Entity
public class Author {
    @Id @GeneratedValue
    public Long id;
    public String name;
}
----

And link it to `Book`:

[source,java]
----
@ManyToOne
public Author author;
----

With a managed session, you can load a book, change its author, and Hibernate will detect the change and flush it to the database at transaction commit without an explicit save call:

[source,java]
----
@Inject
Session session;

@PUT
@Path("/{id}/author")
@Transactional
public Book setAuthor(Long bookId, Long authorId) {
    Book book = session.find(Book.class, bookId);
    book.author = session.find(Author.class, authorId);
    return book;
}
----

You can mix both styles in the same application: use repositories for standard CRUD and queries, and inject `Session` when you need managed operations.
Since Jakarta Data repositories are backed by `StatelessSession`, operations that require a persistence context (lazy loading, cascading persists, dirty checking) need to happen outside the repository, in your service or resource class.

To see the difference, let's create a book with its author using the stateless repository.
You need to save the author first, then the book, because there is no persistence context to cascade the insert:

[source,java]
----
@Inject
BookRepository books;

@Inject
AuthorRepository authors;

@POST
@Path("/with-author")
@Transactional
public Book createWithAuthor(String title, String isbn, int price, String authorName) {
    Author author = new Author();
    author.name = authorName;
    authors.save(author);

    Book book = new Book();
    book.title = title;
    book.isbn = isbn;
    book.price = price;
    book.author = author;
    return books.save(book);
}
----

With a managed `Session`, Hibernate handles this for you:

[source,java]
----
@Inject
Session session;

@POST
@Path("/with-author")
@Transactional
public Book createWithAuthor(String title, String isbn, int price, String authorName) {
    Author author = new Author();
    author.name = authorName;

    Book book = new Book();
    book.title = title;
    book.isbn = isbn;
    book.price = price;
    book.author = author;
    session.persist(book);
    return book;
}
----

Because `Book.author` is a managed association, Hibernate persists the author automatically when you persist the book.

With https://jakarta.ee/specifications/data/1.1/[Jakarta Data 1.1], you will be able to do the same thing inside a repository using `@Persist` instead of `@Save`.
`@Persist` makes the repository stateful, backed by a persistence context instead of a `StatelessSession`:

[source,java]
----
@Repository
public interface BookRepository {

    @Persist
    Book persist(Book book);
}
----

The endpoint then becomes identical to the managed `Session` version, but using the repository:

[source,java]
----
@Inject
BookRepository books;

@POST
@Path("/with-author")
@Transactional
public Book createWithAuthor(String title, String isbn, int price, String authorName) {
    Author author = new Author();
    author.name = authorName;

    Book book = new Book();
    book.title = title;
    book.isbn = isbn;
    book.price = price;
    book.author = author;
    return books.persist(book);
}
----

== What about Panache 1?

Panache 1 is not going away.
It will remain available as an extension for existing applications, and we have no plans to remove it.

That said, Quarkus Data Hibernate is where all new development and investment is happening.
We are working on migration tooling to help existing Panache 1 users transition when they are ready, and we will share more details as that work progresses.

We are also revamping the documentation to be more opinionated and guide users toward a clear path, and improving test coverage so that generated projects include working tests out of the box.
